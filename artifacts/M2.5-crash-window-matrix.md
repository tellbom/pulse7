## 0. 开发原则复述（本项目长期约束，本表据此判定）

> 以下为项目开发原则原文，判定表（§6）与差距分析（§7）的每一格都必须落在该原则框架内。

### 0.1 禁止自研的是「引擎」

以下形状一旦出现在本项目代码中，立即停止并重新评估选型：

- 通用任务调度器
- 事件重放 / event sourcing replay
- 通用 retry / backoff 抽象层
- workflow DSL 或状态机框架
- 任何面向「多种流程」的通用抽象

### 0.2 允许的是「本项目单一流程的记录」

本项目只有**一种** workflow：LLM ↔ tool 循环。其持久化形态限定为：

- append-only 的消息记录（M2 session 已实现）
- append-only 的 intent / result 记录
- append-only 的审计日志（M2 audit.jsonl 已实现）

**不含调度、不含重放。** 规模超过约 500 行即视为在造引擎，触发 §0.1。

### 0.3 分界线

判断标准是**有没有调度和重放**，不是「有没有写文件」。
M2 已 PASS 的 session 恢复、audit.jsonl、checkpoint manifest 均属 §0.2，合规，不得以「禁止自研」为由重构。

### 0.4 调研前置与出口条款

- 开发任何新机制前，**必须先调研已有开源项目**，能融合复用的优先复用。
- **但**：若调研后不存在满足本项目硬约束的现成品，**允许最小自研**，前提是在报告中列出被否决的候选及否决理由（见 D2）。
- 禁止为了「不自造」而引入 work-in-progress / 明确声明不可用于生产 / 语义等级不匹配的项目。

## 1. 崩溃场景与前提假设

本表覆盖三类崩溃，统称「崩溃」：

1. **进程被强杀**（taskkill / OOM / 句柄耗尽）：OS 存活，所有已 Write 的文件内容到达 OS 缓存并可见。
2. **断电 / 硬复位**：OS 页缓存可能丢失，append-only 文件尾部若干行可能整体消失或撕裂（torn）。
3. **进程 panic / 未捕获异常**：等价于强杀，但 Go runtime 退出前已完成的 `Write` 系统调用同样落盘。

前提假设（判定时不得放宽）：

- **不假设有沙盒文件系统隔离**（任务书 §6.4）：JobObject 降级模式无任何文件系统隔离（`jobobject.go:13-17` 注释原文自认）；即便 Sandboxie 模式，工作区写也经 `OpenFilePath` 直通真实磁盘（评估报告 §2-7）。因此所有按「副作用已真实落盘」判定。
- **不假设崩溃点是原子的**：`os.WriteFile` = truncate + 单次 write，两点之间被杀即产生空文件/半文件（`tools.go:278`、`tools.go:319`）。
- **git 对象库与 ref 更新按 git 自身原子性对待**：内容寻址对象先写、`update-ref` 原子换 ref（`gittools.go:104-139`）。
- **M2 现状不做 fsync**：session / audit / manifest 均为 `O_APPEND` + `Write` + `Close`，无 `Sync()`（`session.go:30-38`、`tools.go:190-202`）。断电丢尾部行是常态而非例外。
- 工具集以任务书 §6.3 的 9 工具为准（`get_time` 无状态、恒为 R0，不占表）。

## 2. 崩溃窗口定义与 M2 代码对应关系

### 2.1 窗口定义（任务书 §6.1 原文）

| 窗口 | 定义 |
|---|---|
| W0 | LLM 已返回 tool_call，Agent 尚未记录任何 intent |
| W1 | intent 已落盘，工具尚未开始执行 |
| W2 | 工具执行中（子进程运行中 / 文件写入中 / git 操作中） |
| W3 | 工具已执行完毕，result 尚未落盘 |
| W4 | result 已落盘，尚未回传给下一次 LLM 请求 |

### 2.2 M2 实现中的物理边界（判定的事实基础）

M2 的 `streamTurn` 一次循环按序完成：收流 → 写 assistant(tool_calls) → 逐 call 执行 → 写 tool result → 下一轮请求（`main.go:244-321`）。五个窗口在代码中的确切位置：

| 窗口 | M2 代码位置 | 物理动作 | 典型时长 |
|---|---|---|---|
| W0 | 流收完到 `pushMsg(assistant)`（`main.go:296-307`） | tool_call 仅存在于内存 | 微秒级 |
| W1 | assistant 消息已写 session 到 `t.Fn` 首条副作用语句 | 空转；**含 shell 确认门等待**（`tools.go:251` → `tools.go:463-476` 的 y/N 交互） | **shell 可达分钟级甚至无限期** |
| W2 | `t.Fn` 执行中 | `os.WriteFile`、`runner.Run` 子进程、git 子进程序列 | 毫秒～`shell-timeout`（默认 120s） |
| W3 | `t.Fn` 返回到 `pushMsg(tool)`（中间夹 audit 写入 `tools.go:186` 与预览打印 `main.go:311-315`） | 结果仅在内存与 audit（只有字节数，无内容） | 毫秒级 |
| W4 | tool result 已写 session 到下一次 `CreateChatCompletionStream` 发出（`main.go:246-252`） | 结果已持久化 | 毫秒～秒级 |

三个对判定至关重要的实现事实：

1. **intent 落盘点在执行之前**：assistant(tool_calls) 消息（含 call_id、tool 名、完整 args）先写入 session，然后才开始执行（`main.go:307-310`）。所以 W1 及之后的窗口里，意图（含 write 的全文、shell 的完整命令行）都可从 session 恢复。
2. **audit 是「已发生」记录**：`r.audit()` 在 `t.Fn` 返回之后才调用（`tools.go:173-188`），且只记 `ts/task/tool/args/ok/result_bytes`，**无 call_id、无 started 标记、无结果内容**。audit 条目存在 ⟹ 执行至少到达 W2 末；不存在 ⟹ 处于 W1 或 W2（二者在记录上同形，见 §7.1）。
3. **一轮可含多个 tool_call**：`calls` 数组逐个执行、逐个写 result（`main.go:308-318`）。第 N 个 call 崩在 W2 时，session 尾部是 `assistant(多call) + tool(result₁)…tool(result_{N-1})`，第 N 个 call dangling。**恢复判定必须逐 call_id 进行，不能按轮次粗判。**

## 3. 恢复策略取值（任务书 §6.2 原文，只能从此表选）

| 代号 | 含义 |
|---|---|
| R0 | 无需处理，重启后自然继续 |
| R1 | 直接重跑（无副作用，天然幂等） |
| R2 | 内容幂等重跑（重跑结果与执行一次相同） |
| R3 | 不自动重跑，必须用户确认 |
| R4 | 走 git rollback 回退到 checkpoint 后重来 |
| R5 | 丢弃本次 tool_call，重新交给 LLM 决策 |
| R6 | 无法安全恢复，任务标记为失败并要求人工介入 |

**R6 的适用范围说明**：R6 不落在任何具体工具×窗口格子上。只要 intent 记录可读（session 尾部完整），每一格都有有界策略；只有当**记录本身丢失到无法判定 intent**（断电吞掉 assistant 消息整行、且 audit/calls 无痕）时，任务进入 R6 兜底——「不知道执行过什么」比「知道执行了一半」更糟。该兜底在 §7.4 的记录设计下被压缩到「断电恰好吞掉 intent 行」的极小概率。

### 4.2 逐格理由

**read**

- W0: `R0 — intent 未落盘则执行必未开始，磁盘零改动，resume 后 LLM 自然重新决策（大概率重发同一 read）。`
- W1: `R1 — 纯读无副作用（tools.go:216-235），重跑即得结果。`
- W2: `R1 — os.ReadFile 执行中崩溃无任何落盘痕迹，重跑安全。`
- W3: `R1 — 结果丢失只是信息损失，重读同一文件即恢复。`
- W4: `R0 — 结果已在 session（main.go:316-318），resume 载入即自然续跑。`

> 注：W4 机理上无需重跑（结果已持久化），按取值表定义归 R0（下同，所有 W4 格均为 R0，不再逐格重复论证）。

**write**

- W0: `R0 — 未记录 intent 则 os.WriteFile 未执行（tools.go:278），磁盘零改动。`
- W1: `R2 — intent 含 path + 完整 content（session 的 tool_calls arguments），重跑写入同样内容，终态与执行一次相同。`
- W2: `R2 — truncate 后写回前被杀会留空文件/半文件，但 intent 自带全文，重跑 WriteFile 直接覆盖成目标内容——write 是唯一自带全文修复材料的变更工具。`
- W3: `R2 — 文件已是目标内容，重跑写同样内容终态不变（created/modified 字样差异不影响语义，见 §7.4 合成优先）。`

**edit**

- W4: `R0 — 结果已在 session。`

**shell**

- W0: `R0 — intent 未落盘则 cmd.exe 尚未启动，零副作用；resume 后 LLM 重新决策，若重发命令会再过确认门（tools.go:463-476）。`

- W0: `R0 — 快照未开始，重启后 LLM 重新决策补拍即可。`

## 5. 重点格与 R3/R4 格的展开论证

### 5.1 shell × W2 / W3（本表最难的一格）

**为什么不能自动恢复。** shell 是唯一「副作用逃逸出工作区」的工具，其作用域包括：

| 副作用类别 | 落点 | git checkpoint 能否回退 |
|---|---|---|
| 工作区内文件写/删 | 真实磁盘（Sandboxie 模式经 OpenFilePath 直通；JobObject 模式直接写） | 能 |
| 工作区外文件写/删 | 真实磁盘（JobObject 无隔离；Sandboxie 模式进容器但容器即机器状态的一部分） | **不能** |
| 注册表写 | Sandboxie 模式虚拟进容器；JobObject 模式真实落盘 | **不能** |
| 网络请求 | 任何沙盒模式都不拦截 | **不能**（不可逆） |
| 进程/系统状态 | JobObject 随 job 句柄关闭整树击杀；脱离 job 的系统级效果（sc/regsrv32 等）残留 | **不能** |

W2 崩溃时，Agent 对「命令执行到哪一条、哪个副作用已发生」**零信息**：wrapper 的 out.txt/ec.txt 随崩溃丢失或残缺（`runner.go:44-50`），audit 无条目（事后写入），run id 不在任何持久记录里。此时自动重跑一条非幂等命令（`del`、`net user`、`curl POST`、注册表写）等于在未知状态上叠加第二次副作用。**这格不存在任何工程手段可以把 R3 降为 R2**——重跑的幂等性判断本身就需要「命令已执行到哪」的信息，而这信息在崩溃中不可恢复。

W3 略好于 W2（命令已跑完），但 exitcode 与输出同样丢失：JobObject 模式下 out.txt/ec.txt 位于 `%USERPROFILE%\.win7-agent\run\<UnixNano id>\`（`runner.go:22-42`），id 是纳秒时间戳、从不落盘，重启后只能扫描目录猜配；且下次启动 `purgeStaleRunDirs(>1h)` 会清除证据（`cleanup.go:42-58`，`main.go:129` 启动即调）。即使找回了输出，「命令完成」也不等于「副作用全部落盘」（输出重定向缓冲、后台子进程脱离 job 等）。

**检测手段（现状极限）。** 恢复器能做的最多是：dangling shell intent（session）+ 无 audit 条目 ⇒ 判 W1/W2；有 audit 条目 ⇒ 判 W3。再往下（命令内进展）不可检测。要改善只能靠新增记录（§7.4：started 事件带 run_dir，使 W3 的 out.txt/ec.txt 可定向回收、W1/W2 可区分）。

**用户看到什么。** REPL 恢复时打印：

```
[恢复] 检测到未完成的 shell 调用（call_id=…，崩溃于执行中/结果未落盘）：
  命令: <完整命令行>
  已知：无法判定该命令执行到了哪一步；其影响可能已落盘且不被 git checkpoint 覆盖。
  选项: [r] 重新执行该命令   [s] 跳过并告知 LLM「被中断」   [a] 中止恢复
```

exec/--yolo 模式（无交互、无确认门）下 shell×W1 同样必须走 R3：无人可确认时按「跳过并告知 LLM」保守处置并写审计，绝不自动重跑。

### 5.2 write × W2（半写入状态——可自愈的一格）

`os.WriteFile` = `OpenFile(TRUNCATE)` + 单次 `Write`（`tools.go:278`）。强杀在两点之间 ⇒ 目标文件被截断为 0 或残留半段；断电还可能留下撕裂页。与 edit 不同，**write 的 intent（session 的 tool_calls arguments）携带完整目标内容**，重跑一次 WriteFile 无条件覆盖出正确终态——无论现场是「未写、空文件、半文件、已写完」，处置动作相同且终态相同。这正是 R2 的定义。判 R2 不依赖检测文件损坏与否；检测只影响要不要在审计里记「疑似半写修复」。附带副作用：MkdirAll 已建的目录无害（`tools.go:273`）；manifest 记录若也丢（W2 中 manifest 在文件写之后才记，`tools.go:284-287`），后果仅是 rollback 时漏清一个 agent-created 文件（垃圾残留，见 §7.3），不是数据破坏。

### 5.3 edit × W2（半写入状态——不能自愈的一格，判 R4）

edit 与 write 共用非原子的 WriteFile（`tools.go:319`），半写现场相同；差别在**修复材料**：edit 的 intent 只有 `old_string/new_string` 片段，没有文件全文。半写文件上重跑 edit 有三种结局：

1. 截断后文件恰不含完整 old_string ⇒ 报 "old_string not found"，文件继续处于损坏态；
2. 截断点在 old_string 之后 ⇒ 替换成功但文件尾部丢失——**静默数据损坏，最坏结局**；
3. 写回已完成（实为 W3 误判成 W2）⇒ 报 not found（可识别）。

结局 2 说明「盲目重跑」在本格不可接受，故判 R4：**以最近 checkpoint 为基底恢复该文件，再重放后续记录在案的变更**（本任务只定义策略，重放的具体形态属 M4+ 设计，且必须遵守 §0 不得演化为通用重放引擎——只允许「恢复这一个文件到该有的样子」的有界操作）。检测分支可三态判定（利用 edit 前置校验 old_string 恰出现一次的不变量，`tools.go:311-317`）：

- 文件含 old_string 恰一次、无 new_string ⇒ 未执行 ⇒ 转 R2 重跑；
- 文件含 new_string、无 old_string ⇒ 已执行 ⇒ 转 W3 处置（合成结果）；
- 两者皆无 ⇒ 半写/损坏 ⇒ R4；**无 checkpoint 基底时升级 R3**（只能请用户裁决，展示 diff 意图与现场）。

用户提示（R3 升级路径）：「文件 X 在编辑中途损坏且无 checkpoint 可回退。已知意图：把 <old> 替换为 <new>。请确认是否以损坏现场为基础人工修复或放弃该文件改动。」

### 5.4 git checkpoint × W2 / W3

**W2。** checkpoint 序列是 add(-A) → write-tree → commit-tree → update-ref（`gittools.go:114-139`），全程**只读工作区、只写对象库与私有 ref**（mode 1 走临时 GIT_INDEX_FILE，用户暂存区零接触，`gittools.go:108-113`；mode 2 写 agent 自有的 bare 库）。逐点崩溃的现场与代价：

| 崩溃点 | 现场 | 代价 |
|---|---|---|
| add / write-tree 中 | 临时 index 文件残缺 | `data\sessions\index-<task>-<seq>.tmp` 垃圾文件（无人清理，见 §7.3） |
| commit-tree 后、update-ref 前 | 孤儿 commit 对象 | 对象库冗余，git gc 可收 |
| update-ref 中 | ref 原子换名，新旧其一 | 无中间态 |
| （mode 2 首次 init 中） | bare 库残缺 | `newGitOps` 已内置删除重试（`gittools.go:39-46`） |

任何一点崩溃，工作区内容不变，重拍一次即得等价快照，故 R2。

**W3。** 「已建立快照」的判据不是结果字符串而是 **ref 的存在性**：`refs/win7-agent/checkpoints/<task>/<seq>`。恢复器用 `for-each-ref refs/win7-agent/checkpoints/` 扫描即可发现全部历史 checkpoint 并合成结果文本，无需重拍，R2。

**跨重启的状态缺口（现状，不改变判定但阻碍实现）。** `g.seq` 是内存计数器、ref 路径按 taskID 隔离（`gittools.go:24, 100-102`），重启后新 run 新 taskID、seq 归零 ⇒ 现有 `Rollback` 代码**找不到旧 run 的 checkpoint**。判定表假设恢复器直接扫 ref 命名空间（ref 本身就是持久记录），该假设的落地缺口记入 §7.2/§7.4。

### 5.5 git rollback × W2（判 R3）

**机械上幂等，策略上必须人工。** restore（mode 1）/reset --hard（mode 2）对同一 ref 重跑会覆盖出同一 worktree 终态，随后 `RemoveCreated` 逐项 stat+删除也幂等（manifest append-only 不回写，`session.go:83-111`）——单看工具函数，R2 成立。判 R3 的理由在工具之外：

1. **不可区分性**：崩溃在 restore 半途，重启时的工作区 =「回滚了一半的现场」。此后用户可能已手工改过文件（重启到恢复运行之间的间隙，可能长达数小时）。自动重跑 restore 会把两类状态一并强制覆盖回 checkpoint——**静默销毁用户在间隙里的手工劳动**，这恰是 rollback 工具设计目的（销毁未检查点改动）的最坏误用。
2. **破坏性不对称**：其余 8 个工具的 R2 重跑最坏产生垃圾文件；rollback 的 R2 重跑最坏产生数据丢失。产品已有「shell 需确认门」的先例（`tools.go:463-476`），对破坏性更大的自动回滚反而无门，是策略倒挂。

**检测手段。** dangling rollback intent（session 尾部，args.to 可解析）+ 无对应 tool result；辅证：worktree 与目标 ref 的差异（`git status --porcelain` / `git diff --stat <ref>`）。注意 W2 与 W3 的机械区分同样靠此 diff：diff 为空且 manifest 有未清项 ⇒ 实为 W3（转 R2 补清理）；diff 非空 ⇒ W1 或 W2（W1 需 started 记录区分，§7.4）。

**用户提示。**

```
[恢复] 检测到未完成的回滚（目标 checkpoint <task>/<seq>）：
  当前工作区与该 checkpoint 的差异:
    <git diff --stat 输出>
  继续回滚将丢弃以上差异；取消则保留现状并告知 LLM 回滚被中断。
  选项: [c] 继续回滚   [k] 保留现状
```

rollback×W1 判 R2 而非 R3：那时什么都没发生，pending 的回滚仍是崩溃前的有效意图，直接补执行即可；唯一升级条件是检测到 intent 时间戳之后工作区出现新改动（文件 mtime 晚于 intent 落盘时间），此时按上面同一提示转人工。

## 6. 边界说明（任务书 §6.4）

1. **shell 副作用范围不限于工作区**（详见 §5.1 表格）：注册表、网络、工作区外文件、系统状态均不被 git checkpoint 覆盖。这直接决定了 shell×W2、shell×W3 **只能** R3——R4（回退 checkpoint）对它们无效，回退不了网络请求，也（在 JobObject 降级态）回退不了注册表与外部文件。
2. **降级模式不提供文件系统隔离**：判定全程不假设沙盒保护。JobObject 仅做进程收容（kill-on-close、内存上限、超时整树击杀，`jobobject.go:80-127`）；Sandboxie 模式下工作区写也经 `OpenFilePath` 直通真实磁盘。因此本表对两种运行态同样成立——不存在「沙盒可用时 shell 可降级为 R2」的情形：Sandboxie 也不隔离网络。
3. **多 call 一轮**：恢复判定按 call_id 逐个分类（§2.2 事实 3），同轮先完成的 call 走各自 W4/R0，dangling 的 call 走其窗口策略。
4. **断电丢尾部行**：所有 append 文件无 fsync（§1）。恢复分类必须以「实际可读的最后完整行」为准；`loadSession` 已容忍断行（unmarshal 失败即跳过该行，`session.go:57`），任何新增记录沿用同一模式即可。断电若吞掉 assistant(tool_calls) 整行，则该 call 无从知晓，任务转 R6 兜底（§3）。
5. **恢复必须在 LLM 循环续跑之前执行**：dangling tool_calls 若不处置直接发给 OpenAI 兼容 API，属非法消息序列（tool_calls 后必须跟 tool 消息），首个请求即报错。恢复器先修补尾部、再放行循环。

## 7. 现状差距（对照 §4 判定的 M2 缺口）

### 7.1 audit.jsonl 记录的是「已发生」还是「将要发生」？能否识别 W1–W3？

**已发生。** `r.audit()` 在工具函数返回之后调用（`tools.go:173-188`），条目字段 `ts/task/tool/args/ok/result_bytes`，无 call_id、无 started 标记、无结果内容。

| 想识别 | audit 能否 | 说明 |
|---|---|---|
| W3 完成边界 | **部分能** | 条目存在 ⟹ 执行已返回（到过 W2 末）。但与 session 的 call 关联只能靠 task+tool+args 字符串匹配（`tools.go:196-199`），同轮两条同名同参调用即歧义 |
| W1 vs W2 | **不能** | 两窗口的记录现场完全同形：session 尾部 dangling assistant(tool_calls) + audit 无对应条目 |
| W2 内部进展 | **不能** | 无任何执行期记录（shell 的 run id、git 的中间步骤均不落盘） |

结论：audit 是合规的审计日志（§0.3），但**不是恢复记录**；它只能回答「跑完没有」，回答不了「跑到哪」。

### 7.2 当前 session 恢复（21 条消息）落在哪个窗口？覆盖与遗漏

`--resume` = `loadSession` 全量载入为对话上下文（`main.go:173-180`、`session.go:46-62`）。真机验证的「21 条消息恢复」证明的是**完整会话**（尾消息非 dangling）的载入。

| 窗口 | 覆盖情况 |
|---|---|
| W0 | **顺带覆盖**：尾消息无 dangling，LLM 自然重新决策（R0 成立） |
| W4 | **覆盖**：尾消息为 tool result，载入即自然续跑（R0 成立） |
| W1 / W2 / W3 | **未覆盖**：尾消息为 assistant(tool_calls) 无对应 tool 消息。直接续跑首个 API 请求即因非法消息序列报错（§6.5）；且无任何机制区分三者、更无按表处置的派发逻辑 |

更深的缺口在**进程态**（resume 只还原对话，不还原状态）：

- `gitOps.seq` 内存计数器 + ref 按 taskID 隔离（`gittools.go:24, 100-102`）：重启后新 run 新 taskID，`Rollback` 解析不到旧 checkpoint——§4 表里 checkpoint/rollback 全部格子的策略在跨重启场景下**当前都落不了地**；
- manifest 按 taskID 开新文件（`main.go:132`）：重启后 `RemoveCreated` 读的是空 manifest，rollback 的清理半边失效；
- shell 的 run id、沙盒 runner 状态、确认门状态：均不跨重启。

### 7.3 checkpoint manifest 当前写入时机，相对 W2 / W3 在前还是在后？

「manifest」在 M2 有两个实体，分别回答：

1. **write/edit 的变更 manifest**（`manifest-<task>.jsonl`，created/modified 记录）：在文件写成功**之后**、工具返回**之前**写入（`tools.go:283-287`、`tools.go:322`）——位于 **W2 尾部、W3 之前**。推论：W2 中途崩溃可能出现「文件已建、manifest 无记录」，rollback 清理时漏删该 agent-created 文件（垃圾残留，非数据破坏）；反向无危害（manifest 有记录而文件未建不可能，因为顺序相反）。
2. **git checkpoint 自身**：没有独立 manifest，「快照已建立」的持久判据就是私有 ref 的存在（`gittools.go:137-139`，update-ref 是序列最后一步）——ref 写入同样位于 **W2 内、W3 之前**。副作用：`data\sessions\` 下的临时 index 文件（`index-<task>-<seq>.tmp`，`gittools.go:110-111`）没有任何清理路径，checkpoint 崩溃残留会永久堆积（M3 清单项，非本任务范围）。

### 7.4 要覆盖全部 45 格，最少需要新增什么记录？（字段清单与行数估算）

**新增一个 append-only 调用生命周期日志**（§0.2 明文允许的「intent / result 记录」形态），与 session 同目录：`calls-<taskID>.jsonl`，三类事件：

| 事件 | 字段 | 写入时机（对应窗口边界） | 关闭的判定缺口 |
|---|---|---|---|
| intent | `ts, task, call_id, tool, args, ws` | 收到 tool_call 即写（pushMsg(assistant) 之后、执行之前） | 把 W0→W1 边界从「微秒级内存窗口」变为可审计落盘点；shell/edit 等的意图不再只依赖 session 单点 |
| started | `ts, call_id, run_dir(shell), ref_seq(checkpoint)` | 紧贴第一条副作用语句之前 | **区分 W1/W2 的唯一依据**；shell 的 run_dir 使 W3 的 out.txt/ec.txt 可定向回收（§5.1） |
| finished | `ts, call_id, ok, effect, result_sha256, result_bytes` | 工具返回后、写 tool result 前同步写 | 区分 W2/W3；`effect`（如 created/modified/rolled-back-to/ref）供合成结果与 Rollback 补清理 |

配套（非日志、属恢复器逻辑）：checkpoint 发现改为 `for-each-ref refs/win7-agent/checkpoints/**` 扫描（ref 即持久记录，替代内存 seq，弥合 §7.2 跨重启缺口）；恢复分类器读 session + calls + audit 三源交叉，按 call_id 逐个落窗（§6.3），再按 §4 表派发处置（合成 tool result / 重跑 / 问询 / 回退）。

**行数估算（不含审计与测试）**：

| 部件 | 预估行数 |
|---|---|
| calls 日志写入器（O_APPEND、容断行，复用 loadSession 模式） | 60–80 |
| 恢复扫描 + 五窗口分类（含 audit 交叉、逐 call_id） | 120–150 |
| 9 工具处置派发（大部分是合成结果与受控重跑；R3 格走问询；edit 三态检测） | 150–200 |
| checkpoint ref 发现辅助 | ~40 |
| shell run_dir 贯通（runner 返回 id → started 事件） | ~20 |
| **合计** | **≈ 390–490 行** |

贴着 §0.2 的 500 行红线下沿，成立的前提是严格保持三不变：**无调度**（恢复器只在启动时跑一次）、**无重放引擎**（edit 的 R4 只做「恢复这一个文件」的有界操作）、**无通用抽象**（事件类型固定三类，不为「未来其他流程」预留字段）。任何超出即触发 §0.1 停止条款。

**处置分布总账**（45 格 vs 记录完备后的可自动化程度）：R0 18 格 + 纯读 R1 12 格 + R2 12 格 = 42 格可全自动处置；R3 3 格（shell×W2/W3、rollback×W2）+ R4 1 格（edit×W2）必须人机交互或 checkpoint 基底；升级路径 3 处（§4.1）。**当前 M2 无任何恢复器，45 格中除「碰巧尾消息完整」的 W0/W4（18 格，由 --resume 顺带覆盖）外全部悬空。**

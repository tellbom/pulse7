## 0. 项目硬约束（筛选依据，不可放宽）

```
Go 1.20.14
CGO_ENABLED=0
GOOS=windows GOARCH=amd64
目标系统 Windows 7 SP1 x64（可能缺 KB4474419）
交付形态：单 EXE + runtime\git + 本地数据文件
内网离线交付，无公网依赖
禁止：Redis / 独立服务端 / Docker / Python / Node / CGO runtime / 监听 TCP 端口
```

两条背景事实使约束进一步收紧（后文多处引用）：

1. **Go 1.21 起官方放弃 Windows 7**：Go 1.21 Release Notes 原文 *"Go 1.21 requires at least Windows 10 or Windows Server 2016; support for previous versions has been discontinued."*（[go.dev/doc/go1.21](https://go.dev/doc/go1.21)）。本项目锁 Go 1.20.14 正因此。任何 go.mod 声明 `go ≥ 1.21` 的依赖，用 1.20 工具链编译直接报错；即便换新工具链编过，产物在 Win7 上官方不支持。
2. **语义等级是一票否决项**（任务书 §8.3）：D1 判定表的核心难题格（shell×W2/W3、edit×W2、rollback×W2）全部要求「先判定窗口、再问人或回退」，而引擎对未完成的 activity 只有一个动作——重新派发执行。若引擎只提供 at-least-once，它无法覆盖这些格子，引入它的工作量收益为零。

## 4. durabletask-go 附加核查（任务书 §8.4）

### 4.1 是否存在不监听 TCP 端口的纯进程内模式？是否官方支持路径？

**存在，且为官方文档路径。** README「Embedded orchestrations」一节原文：*"It's also possible to write orchestrations directly in Go and run them in the local process."*，并给出官方示例形态：`task.NewTaskRegistry()` + `AddOrchestratorN/AddActivityN` + 进程内 `client, worker := Init(ctx, r)`（TaskHubClient/TaskHubWorker 直接跑在 SQLite backend 上，仓库 samples 目录配同一模式）。gRPC/TCP（`WithTaskHubGrpcClient`、默认 4001 端口的 sidecar）**只**是跨语言编排（dotnet worker）所需。同节的官方保留意见原文：*"The full set of Durable Task features is not yet available as part of the Go SDK, but will be added over time."*——进程内模式被官方自认不完整。

结论：纯进程内、零 TCP 的用法成立；但这不改变 at-least-once 语义与 WIP 状态两个否决项。

### 4.2 SQLite 驱动与 Windows 7 兼容性

- 驱动为 **`modernc.org/sqlite`（纯 Go，非 CGO）**：v0.5.0 锁 v1.22.1（2023 年版，go.mod 声明在 Go 1.20 能力内）；dapr master 线随 go 1.26 使用新版。
- **Win7 兼容性无公开验证**：modernc 系（sqlite/libc）无任何 Windows 7 支持声明或 CI 覆盖；关键事实链：Go 1.21+ 官方放弃 Win7 ⇒ 新版 modernc 随新工具链发布后，其产物在 Win7 上无任何保证；已知明确不支持 windows/386。社区先例（sqlbless、HackBrowserData 等）均以「Go 1.20 工具链 + 旧版 modernc」维持 Win7 交付——**「能跑」是社区经验，不是上游承诺**。
- 文件锁层面：SQLite Windows VFS 走 LockFile 族 API（Win7 存在），但经 modernc 的 libc 翻译层实现，对该层在老 Windows 上的行为无公开测试记录。生产内网交付前必须真机 gate（本任务不做 POC，gate 留给后续里程碑决策）。

### 4.3 history 存储机制（全量存储 + 全量重放）

对 backend/sqlite/sqlite.go 的直接代码核验：

1. **activity 输入输出全量入库**：orchestration 启动输入全量存 `Instances.Input` 并冗余进 History（`ExecutionStarted`）；activity 派发时输入存 `NewTasks.Data`，完成时该行删除并把**完整输出**写入 History 的 `TaskCompleted.Data`。
2. **单次推进全量重放**：`GetOrchestrationRuntimeState` 每次执行 `SELECT … FROM History WHERE InstanceID=? ORDER BY SequenceNumber`——**无增量游标、无检查点压缩**，orchestrator 函数每轮从第一个事件重放到当前（这正是 DTFx 家族强制 orchestrator 确定性的原因，与 go-workflows 的确定性限制同源）。
3. 推论：对「LLM↔tool 循环」这种长历史会话，history 表按消息与工具结果全量膨胀，每次推进全量拉取——哪怕引擎可引入，这也是与 `max-ctx` 截断策略（main.go:324-334）正面冲突的负载模型。

| River | ✅ at-least-once | ✅ **PostgreSQL（独立服务端）** + go 1.26 + MPL-2.0 负担 | — |

**没有一个候选能同时通过三关。** 语义关全军覆没：7/7 为 at-least-once——这不是选型失误，而是领域共识（分布式崩溃恢复下 exactly-once 执行不存在，只能 exactly-once **状态效果**，而那正是引擎方要求使用方自证幂等的原因）。Go 版本关 6/7 超线（唯一例外是 durabletask-go 已停更的 v0.5.0 旧线）。存储/服务关 4/7 直接踩明文禁止项。

## 6. 结论（§9，二选一裁决）

### 裁决：全部否决，最小自研

**为什么引擎覆盖不了 R3/R4/R6 格（采纳路径的反证）。** 引擎对「未完成 activity」的唯一处置是**重新派发执行**（锁过期→重派），它把 D1 判定表里的每一格都强制当作 R1/R2 处理：

- `shell×W2/W3`（R3）：引擎会在副作用未知的现场盲目重放非幂等命令——正是 D1 §5.1 判定「不存在工程手段可降级」的那格；
- `edit×W2`（R4）：引擎重派 edit 落在半写文件上，命中 D1 §5.3 列出的「静默数据损坏」结局；
- `rollback×W2`（R3）：引擎重派破坏性回滚，销毁用户在重启间隙的手工修改。

即：**引擎解决的是「调度与重派」（本项目明确不要，开发原则 §0.1），回答不了「该不该重派」（本项目唯一的问题）**。幂等性判断在引擎方案下仍须本项目逐格给出（引擎文档自己也这么要求），故「引入引擎」= 自研全部判定逻辑 + 额外背负 go 版本/存储/Win7/许可证四重违约。与任务书 §1 的预判一致。

**出口条款触发（开发原则 §0.4）**：上表已列 7 个被否决候选及否决理由，且不存在满足硬约束的现成品——允许最小自研。

### 最小自研方案轮廓（§0.2 框架内，不含代码）

方案即 D1 §7.4 的设计，此处只给轮廓与合规论证：

1. **记录形态**：单一 append-only 调用生命周期日志 `calls-<taskID>.jsonl`，固定三类事件——
   - `intent`：`ts, task, call_id, tool, args, ws`（收到即写）；
   - `started`：`ts, call_id, run_dir(shell), ref_seq(checkpoint)`（贴副作用前写）；
   - `finished`：`ts, call_id, ok, effect, result_sha256, result_bytes`（返回后写）。
   容断行沿用 `loadSession` 既有模式（unmarshal 失败跳行，session.go:57）。
2. **恢复器**：仅启动期运行一次——读 session + calls + audit 三源交叉，按 call_id 逐个落窗（W0–W4），再按 D1 §4 表逐格派发（合成 tool result / 受控重跑 / 问询 / checkpoint 回退）。**无调度器、无事件重放引擎、无 retry 抽象、无 DSL**（§0.1 四禁全不触碰）；checkpoint 跨重启改由 `for-each-ref` 扫描发现（ref 即持久记录），顺带修复 M2 的 `seq` 内存计数器缺口。
3. **规模**：约 **390–490 行**（分项估算见 D1 §7.4），贴 500 行红线下沿；超限即触发 §0.1 停止条款重新评估。
4. **对 R3/R4/R6 的覆盖**：R3 格（shell×W2/W3、rollback×W2）由「started/finished 事件精确落窗 + 问询交互」覆盖——引擎给不了的「先判定、再问人」正是恢复器的全部职责；R4 格（edit×W2）由「intent 里的 old/new + checkpoint 基底」支撑有界修复；R6 兜底仅剩「断电吞掉 intent 行」的极小概率（§3 of D1）。
5. **依赖变化**：零新增第三方依赖；继续 Go 1.20.14 / CGO_ENABLED=0 / 单 EXE 形态，与 M3 安装器任务无交集。

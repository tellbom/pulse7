## 0.5 判断准则（歧义时按此判断方向；仍需新增本文件未列出的行为则**停止并报告**）

1. **高自治**：不建造二次猜测模型推理的机制。**杀掉进程等于让模型失去观察能力**——这正是本任务书要纠正的。该不该终止某个进程，由模型或用户判断，系统只负责如实记录。
2. **低摩擦**：不新增确认门、不新增必须由用户回答才能继续的提示。
3. **强可见**：凡是系统替用户做了处理——收割、告警、降级、放弃清理——都必须留痕。**可见性不打断执行、成本为零。**
4. **保留低成本事实校验**：路径解析、文件新鲜度、流终止、编码判定全部保留。
5. **错误可恢复优先于错误静默**：不能恢复的明确报错，**任何情况下不许静默继续**。
6. **不对自己不知道的事实装作知道**：进程还在 ≠ 任务进展正常；受限模式必须持续可见；**记录里的 PID 不等于当前那个 PID**——见 H4 的身份核对。

## 背景：这份任务书解决两个不同的问题

**问题一：进程活不到下一条命令。**
现状每条 shell 命令一个 JobObject，命令结束即 `KILL_ON_JOB_CLOSE` 整树击杀。于是"命令1 启动服务 → 命令2 使用它"做不到——第二条命令执行时进程已经没了。**进程没了，模型就无法再检查它的输出与状态，任务链条断在这里。**

**问题二：长命令堵住当前这一轮。**
一次二十分钟的构建会把整个对话阻塞。需要的是立即返回、输出可查、可终止。**这与进程存活无关。**

**为什么退出时仍然收割。**
用户是 IT 与技术岗，残留进程本身不是严重问题。但本项目曾因进程资源耗尽导致整个用户态失去响应，靠宿主机硬复位恢复，**Win7 在这方面比 Win10/11 脆弱得多**。会话级 Job 的退出收割是内核保证、代码已有、零成本。**主动扔掉一个免费且能防住已知事故的机制，换不到任何东西。**

需要活过退出的进程走 `detached` 显式声明——**"尽力而为"只出现在这一处**。

## H1 —— Job 归属提升到会话级

- **会话级 Job 在 pulse7 启动时创建**，保留 `KILL_ON_JOB_CLOSE`；
- shell 命令进程创建时**分配到会话级 Job**，不再每条命令新建 Job；
- 命令进程本身跑完照常退出，**它启动的子进程继续存活**，直到 pulse7 退出时由会话级 Job 统一收割。

```
命令1: start chrome.exe --remote-debugging-port=9222   → cmd 退出，chrome 存活
命令2: curl http://localhost:9222/json                 → 能连上上一条命令启动的 chrome
pulse7 退出                                            → chrome 随会话级 Job 被收走
```

**必须先消除的窗口**：挂起创建 → 分配 Job → 恢复线程。否则子进程可能在被分配之前逃出会话 Job。按 H0 清点结果，已正确则沿用，未正确则修正。

**Job 分配失败**（SSH 会话、嵌套 Job 等）：

- 进入**受限模式**并**持续可见地告知**用户，不得只在任务结束时补一句；
- 明确说清受限模式下不保证退出时的确定性清理；
- **不得因分配失败就静默回退到旧的每命令 Job 模型。**

## H2 —— 前台命令超时仍击杀整棵子树（**不得一并放宽**）

否则 `shell_timeout` 形同虚设——命令超时了、模型拿不到结果、进程还在后台跑且无人管理，**是最糟的状态**。

超时路径需要能定位并终止**该命令派生的进程树**。可选方案：按进程树遍历，或为超时敏感的命令单独建子 Job 挂在会话 Job 下。**方案由你评估后选定并说明理由**，必须能在真机上核验进程表确认整树已终止。

## H3 —— 进程登记表（**本轮新增，用户裁决**）

系统只负责如实记录，**该不该终止由模型或用户判断**（§0.5 第 1 条）。

### 记录内容

每个由 pulse7 启动的进程（含 shell 前台命令、后台任务、detached）登记：

| 字段 | 说明 |
|---|---|
| 命令原文 | |
| PID | |
| **进程创建时间** | **身份核对必需，不得省略** |
| **映像路径** | **身份核对必需，不得省略** |

| 状态 | 运行中 / 已结束 / 被终止 / detached |

### 暴露方式

- REPL `/tasks`：列出当前会话的进程与后台任务概况；
- 事件流：进程创建、结束、被终止各发一条，供前端常驻面板使用；

### 不做

不做进程健康检查、不做自动重启、不做资源占用采样。**只记事实。**

## H4 —— `detached` 与跨会话记录（**含身份核对裁决**）

### `detached` 选项

- `shell` 工具增加 `detached`（布尔，**默认 `false`）；
- `detached=true` 的进程**不加入会话 Job**，pulse7 退出后继续存活；
- **这是"尽力而为"唯一该出现的地方**——只有显式声明的进程才放弃清理保证；
- 使用时必须在输出中明确告知「该进程将在 pulse7 退出后继续运行」，并记入审计；
- 工具描述中说明：**默认不要用**，仅用于用户明确要求长期驻留的服务。

### 退出时

打印两份清单：① 被收割的进程；② **detached 留下来的**（命令 + PID + 创建时间），并**落盘持久化**，供下次启动读取。

### 下次启动：展示，核对身份后才可终止（**本项最要紧**）

**Windows 会积极复用 PID。昨天记下的 PID 4012，今天可能是别人的进程。** 照着记录去杀，就是对一个无法核实的事实下手（§0.5 第 6 条），而代价是杀错进程。

因此：

- 启动时读取上次留下的 detached 清单，**展示**给用户与模型，标明这是**上一会话留下的记录，未经核实**；
- 提供终止入口（模型可调用、用户可手动），但**终止前必须核对身份三元组：PID + 进程创建时间 + 映像路径，三项全部匹配才允许终止**；
- **核对不通过时，明确报告"无法确认该 PID 仍是原进程"并拒绝终止**，不得杀、不得静默跳过；
- **不做自动清理**：启动时不主动终止任何上次留下的进程。

## H5 —— 后台长时任务（按 H0 清点，缺什么补什么）

不阻塞当轮对话，且能被查询与终止。

- **`shell` 增加 `background` 参数**：`false`（默认）前台执行，行为与 H1 之后的前台路径一致；`true` 立即返回 `task_id`，输出持续写入 `data\tasks\<task_id>.output`；
- 工具描述说明适用场景（长时构建、需持续观察输出的服务），并说明**绝大多数命令应当用前台**；
- 会话任务表：`task_id → {命令, 进程, 输出文件, 启动时间, 状态, 退出码}`，与 H3 登记表打通，不重复造第二套记录；
- **只新增这两个工具，不要扩展**：

| 工具 | 作用 |
|---|---|
| `task_output` | 按 task_id 拉取输出，支持 offset 增量读取（复用 `read` 分页的实现思路） |
| `task_kill` | 按 task_id 终止后台任务（整树） |

- REPL `/tasks` 列出运行中的后台任务（task_id、命令、运行时长、输出大小、状态）。

### 上限：只保留一条硬上限，其余为告警

| 项 | 值 | 形式 | 配置项 |
|---|---|---|---|
| 单任务输出文件大小 | 50 MB | **硬上限**，超出截断并标注 | `background_task_max_output_mb` |
| 并发后台任务数 | 5 | **告警**，不拒绝 | `background_task_warn_count` |
| 单任务运行时长 | 60 分钟 | **告警**，不终止 | `background_task_warn_sec` |

输出文件之所以是硬上限：**磁盘写满会影响整台机器，且用户无法预见**——这不是"残留进程"那种用户能自行处理的问题。

### 退出清理

正常退出、`EXEC-ERROR`、Ctrl-C 两次强退、panic —— **四条路径都由会话级 Job 统一收割**，依托 `KILL_ON_JOB_CLOSE`，不是逐个发信号。退出时一并打印被收割的后台任务清单。

### 明确不做：持久 shell 会话

现有输出捕获建立在"命令退出 → 读 `out.txt` / `ec.txt`"之上；持久 shell 中命令永不退出，需改为"喂 stdin + 读哨兵 + 另想办法取退出码"，**Sandboxie 与 JobObject 两条 wrapper 链路都要重写**——那是本项目迭代最多、最脆弱的一块代码。收益仅限 `cd` / `set` 跨命令保留，而 `cd x && cmd` 基本可覆盖。**若真实试用中反复出现相关问题，再单独评估。**

## H6 —— 进程堆积：告警，不拦截

- 会话 Job 内进程数超过阈值（默认 **50**，配置项 `process_warn_threshold`）时，打印一行提示，告知当前进程数并建议清理；
- **不拒绝新建进程、不自动杀任何东西**——信息给到，决定权在用户；
- `/tasks` 中可查看当前会话进程概况。

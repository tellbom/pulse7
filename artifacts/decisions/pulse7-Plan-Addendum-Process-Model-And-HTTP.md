## 决策一：进程模型从「命令级围栏」改为「会话级围栏」

### 变更内容

**现状**：每条 shell 命令一个 JobObject，命令结束即 `KILL_ON_JOB_CLOSE` 整树击杀。
**改为**：JobObject 归属提升到**会话级**。命令进程本身跑完照常退出，但它启动的子进程**继续存活**，直到 pulse7 退出时由会话级 Job 统一收割。

```
命令1: start chrome.exe --remote-debugging-port=9222   → cmd 退出，chrome 存活
命令2: curl http://localhost:9222/json                 → 能连上上一条命令启动的 chrome
...
pulse7 退出                                            → chrome 随会话级 Job 被收走
```

### 为什么改

1. **当前模型主动排除了合法工作流**。「上一条命令启动、下一条命令使用」是编程 Agent 的常见需求（浏览器自动化、开发服务器、后台编译）。市面上的同类工具都没有把命令绑死在 Job 上。
2. **杀掉进程等于让 Agent 失去观察能力**。进程没了，模型就无法再检查它的输出与状态，任务链条断在这里。
3. **残留进程对目标用户不是严重问题**。用户是 IT 与技术岗，任务管理器里看到残留自己会处理。为消除一个用户能自行解决的小麻烦而砍掉一整类工作流，不划算。

### 为什么仍然要用 Job，而不是不用

会话级 Job **在提供上述全部灵活性的同时**，额外白送一项别的实现拿不到的能力：**pulse7 退出时的清理是内核保证的确定性行为**，不是「尽力而为」。

Claude Code 想做到的正是这件事，它靠信号链去做，因而有一系列已知泄漏缺陷（进程活过会话结束、后台任务中途被杀、输出文件吃掉数百 GB）。Windows 的 Job 对象是内核级机制，反而更可靠。

**不要因为「允许泄漏」就把 Job 一起去掉——那是把白送的确定性也扔了。**

### 实现要点

- 会话级 Job 在 pulse7 启动时创建，保留 `KILL_ON_JOB_CLOSE`；
- shell 命令进程创建时分配到**会话级** Job，不再每条命令新建 Job；
- **A7（P1-06）的挂起创建 → 分配 Job → 恢复** 的修复对本项同样适用且是前提：必须消除「先启动、后分配」的窗口，否则子进程可能逃出会话 Job；
- Job 分配失败（SSH / 嵌套 Job 场景）时，按 A7 规定进入受限模式并**持续可见地告知**，不得只在结束时追一句。

### 必须保留的行为（**不得一并放宽**）

**前台命令超时仍然击杀该命令的整棵子树。**

理由：否则 `shell_timeout` 形同虚设——命令超时了、模型拿不到结果、进程还在后台跑且无人管理，是最糟的状态。Claude Code 同样是超时即杀掉 shell 及其启动的所有进程。

实现上：超时路径需要能定位并终止该命令派生的进程树（例如按进程树遍历，或为超时敏感的命令单独建子 Job 挂在会话 Job 下）。**具体方案由你评估后选定并说明理由。**

### 新增 `detached` 选项（给需要活过 pulse7 的进程）

- `shell` 工具增加 `detached`（布尔，默认 `false`）；
- `detached=true` 的进程**不加入会话 Job**，pulse7 退出后继续存活；
- 这是「尽力而为」唯一该出现的地方——**只有显式声明的进程才放弃清理保证，不是所有进程**；
- 使用时必须在输出中明确告知用户「该进程将在 pulse7 退出后继续运行」，并记入审计；
- 工具描述中说明：**默认不要用**，仅用于用户明确要求长期驻留的服务。

### Win7 进程堆积：告警，不拦截

本项目踩过一次进程资源耗尽导致整个用户态失去响应，靠宿主机硬复位恢复（评估报告 §12.3）。Win7 在这方面比 Win10/11 脆弱。

因此保留一条**告警**（不是限制）：

- 会话 Job 内进程数超过阈值（默认 50，配置项 `process_warn_threshold`）时，打印一行提示，告知当前进程数并建议清理；
- **不拒绝新建进程、不自动杀任何东西**——信息给到，决定权在用户；
- `/tasks`（见下）中可查看当前会话进程概况。

## 决策二：后台长时任务（对标 Claude Code `run_in_background`）

B4 需求已澄清：需要的是**后台长时进程管理**，不是放宽 Job 约束。

会话级 Job 已经解决了「跨命令存活」，本项解决的是另一半：**不阻塞当轮对话，且能被查询与终止**。

### B4.1 `shell` 增加 `background` 参数

- `background=false`（默认）：前台执行，等待完成后返回结果——**行为与决策一之后的前台路径一致**；
- `background=true`：立即返回 `task_id`，不阻塞当轮；输出持续写入 `data\tasks\<task_id>.output`；
- 工具描述说明适用场景（长时构建、需要持续观察输出的服务），并说明绝大多数命令应当用前台。

### B4.2 会话任务表与两个新工具

维护 `task_id → {命令, 进程, 输出文件, 启动时间, 状态, 退出码}`。

**只新增这两个工具，不要扩展**：

| 工具 | 作用 |
|---|---|
| `task_output` | 按 task_id 拉取输出，支持 offset 增量读取（复用 `read` 分页的实现思路） |
| `task_kill` | 按 task_id 终止后台任务（整树） |

REPL 增加 `/tasks`：列出运行中的后台任务（task_id、命令、运行时长、输出大小、状态）。

### B4.3 上限：只保留一条硬上限，其余为告警

Claude Code 的泄漏问题来自约束不足，但本项目的用户明确接受残留。因此**只保留一条真正必要的硬上限**：

| 项 | 值 | 形式 | 配置项 |
|---|---|---|---|
| 单任务输出文件大小 | 50 MB | **硬上限**，超出截断并标注 | `background_task_max_output_mb` |
| 并发后台任务数 | 5 | **告警**，不拒绝 | `background_task_warn_count` |
| 单任务运行时长 | 60 分钟 | **告警**，不终止 | `background_task_warn_sec` |

输出文件之所以是硬上限：磁盘写满会影响整台机器，且用户无法预见——这不是「残留进程」那种用户能自行处理的问题。（Claude Code 有后台任务输出吃掉数百 GB 磁盘的实际案例。）

### B4.4 退出清理

- 正常退出、`EXEC-ERROR`、Ctrl-C 两次强退、panic —— **四条路径都由会话级 Job 统一收割**，依托 `KILL_ON_JOB_CLOSE`，不是逐个发信号；
- `detached=true` 的进程按定义不在收割范围内，但**退出时必须打印它们的清单**（命令 + PID），让用户知道有什么留了下来；
- 退出时一并打印被收割的后台任务清单。

### B4.5 明确不做：持久 shell 会话

Claude Code 还维持一个会话级持久 bash 进程，使 `cd`、`set` 等 **shell 自身状态**跨命令保留。

**本项不做**，理由是代价与收益不成比例：

- 现有输出捕获机制建立在「命令退出 → 读 `out.txt` / `ec.txt`」之上。持久 shell 中命令永不退出，需改为「喂 stdin + 读到哨兵标记 + 另想办法取退出码」，**Sandboxie 与 JobObject 两条 wrapper 链路都要重写**——那是本项目迭代轮次最多、最脆弱的一块代码；
- 收益仅限于 `cd` / `set` 的跨命令保留，而 `cd x && cmd` 基本可覆盖；
- 会话级 Job（决策一）已经解决了真正重要的那部分——**子进程跨命令存活**。

**若真实试用中反复出现因此产生的问题，再单独评估。**

### B4 与决策一的合并验收

| # | 标准 |
|---|---|
| 1 | 「命令1 启动进程 → 命令2 使用该进程」跨命令场景真机跑通 |
| 2 | 前台命令**超时**时，该命令的子进程树被击杀（真机核验进程表） |
| 3 | pulse7 四条退出路径**各自**验证：会话 Job 内进程全部被收割，无残留（真机核验进程表） |
| 4 | `detached=true` 的进程在 pulse7 退出后确实存活，且退出时打印了清单 |
| 5 | 后台任务跨多轮对话存活，`task_output` 能拉到增量输出，`task_kill` 整树终止 |
| 6 | 输出文件硬上限触发后正确截断并标注；两项告警在阈值处正确打印且**不阻断执行** |
| 7 | Job 分配失败环境（SSH 会话）下进入受限模式，且状态持续可见 |
| 8 | 进程数告警阈值触发后正确打印，且**不拒绝新建进程** |
| 9 | 连续启动/终止 20 次后台任务后系统响应正常（Win7 资源风险回归） |
| 10 | 现有 shell 相关用例（含连续 20 次 shell、S1/S2/S3/R1/R2、Gate A/B）全部无退化 |

## 决策三：本地 TCP 监听已获批准

用户明确放行：**允许本地监听 TCP 端口**（与内网既有服务同类形态）。

主计划阶段三中「必须由用户显式决策后才能突破」的限制**已解除**，HTTP 层可以实现。

以下缓解措施**仍然全部执行**：

- 仅绑定 `127.0.0.1`，**不得绑 `0.0.0.0`**；
- 随机端口，不使用固定端口；
- 启动时生成一次性 token，前端必须携带才能访问；
- 进程退出即关闭监听；
- `doctor` 与界面上明示监听地址、端口与状态。

**仍需人工提供**：内网 Win7 目标机上装的浏览器与版本。Vue 3 依赖 ES2015 Proxy，IE 内核无法运行；Win7 上可用的现代浏览器实际只剩 Chrome 109 与 Firefox 115 ESR。**不影响后端开工**，但影响 Vite 的 `build.target` 与降级提示文案。

## 接口契约文档（C1）追加条目

主计划 C1 的三部分各追加：

**数据模型**追加：

- 后台任务：task_id、命令、状态（运行中/已结束/被终止/输出超限截断）、启动时间、运行时长、输出文件大小、退出码
- 会话进程概况：当前会话 Job 内进程数、是否已超告警阈值
- detached 进程清单：命令、PID、启动时间
- 权限档位与规则的当前生效值
- 监听状态：地址、端口、token 有效性

**操作接口**追加：

- 后台任务：列表、拉取输出（支持增量 offset）、终止
- 权限档位切换（含即时生效说明）

**事件流**追加：

- 后台任务启动（task_id、命令）
- 后台任务**有新输出**（**主动推送，不要让前端轮询**——参考 Claude Code 的 system-reminder 机制）
- 后台任务结束（正常 / 被终止 / 输出超限，退出码）
- 告警触发（进程数 / 并发任务数 / 任务时长）
- detached 进程创建（含「将在退出后继续运行」的明确标注）

**并明确一条**：前端对后台任务与进程概况的展示应当**常驻可见**（侧边栏或状态栏），而不是埋在对话流里——后台任务的价值就在于它脱离了当前对话轮次。

## 阶段三调整后的范围

1. **C1 接口契约文档**（含本文件追加条目）——首要交付物，供用户做界面设计；
2. **C2 执行/呈现解耦**——CLI 输出与 rc-0.7 逐行一致，不得退化；
3. **C3 HTTP 层实现**——按契约实现接口与事件流（事件流建议 SSE，与现有 LLM 流式处理同构）；
4. **C4 静态资源托管**——`go:embed` 内嵌前端构建产物，保持单 exe；本阶段只做**最小占位页面**验证链路，真正的前端由用户另行安排。

阶段三验收追加：

| # | 标准 |
|---|---|
| 6 | HTTP 层只绑 127.0.0.1、随机端口、token 校验有效（非法请求被拒的用例） |

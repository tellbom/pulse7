## F1 —— 截断不得删除模型尚未消费的最新工具结果（**最高优先级**）

### 问题

位置：`agent/ctxcompress.go:87-88`、`159-168`、`172-190`。

不足三组工具轮次且超过 65% 阈值时直接进入 truncate，可删除范围只保护 system 与最后一条 user，**不保护最新的工具调用/结果组**。

复核已独立复现：system + 用户任务 + 一组目录观察结果，`maxCtx=12000` 时请求从 **15273 字节被砍到 91 字节，只剩两条消息，最新工具结果全部消失**。

### 为什么这条最重要

它给出了长期观察到的 R2 探索不收敛的**确定性机制解释**：

```
模型 tree → 拿到目录结构 → 上下文超阈值 → 截断删掉刚拿到的结果
→ 模型看不到自己刚查的东西 → 再 tree 一次 → 再被删 → 循环直到触顶
```

**此前把该现象归因于"模型探索策略差"是错的。** 模型反复 tree/ls 是对失忆的正常反应。

**这个洞是本任务包上一轮修 C-10（短历史逃逸口）时引入的**——原任务书只写了"补上截断兜底"，未写"必须保住最近一组"，属规格缺失。本次把该分支的规格写全，见下。

### 改法

**1. 不可删除范围增加"最近一组"**

- 截断的不可删除范围增加：**最近一组完整的工具调用及其对应的 tool result**。
- 该保护与 system、最后一条 user 同级，**任何路径下都不得删除**。
- 保留数量的下限强制为 **1**（注意 Go 切片 `[len-0:]` 之类的边界写法会返回全量或空，必须显式处理）。

**2. 单组超预算时的降级顺序（**照此实现，不要自行设计**）**

当 system + 最后一条 user + 最近一组仍超出预算时，**按以下固定顺序削减，不得跳步、不得改序**：

| 步骤 | 削减对象 | 下限 |
|---|---|---|
| ① | 工具结果正文，保留头部 | 2 KB → 最低 512 B |
| ② | 工具调用参数摘要 | 200 B → 最低 64 B |
| ③ | 工具名与 tool_call_id | **不可削减**，必须完整保留 |
| ④ | ①②削到下限仍超预算 | 见下条 |

- **上表的四个数值是源码内常量，不得成为配置项、不得成为命令行参数**（§1.1）。
- 削减后必须留下**明确的截断标记**，标记中必须包含：**原始字节数、已丢弃字节数**。只写"[truncated]"不合格——那是对用户装作没发生过（§0.5 第 6 条）。
- **④ 的处理**：先读源码确认当前是否已有"上下文超限可恢复"路径（紧急压缩后重试一次）。
  - **已有** → 接入该路径，**不要新建**；
  - **没有** → 明确报错并中止本轮，同时记入 `f1f4-findings.md`。
  - **两种情况下都不许静默发出超预算请求，也不许在本任务包内新建恢复机制。**

**3. 不得借机扩建**

> 对标依据：`CC:services/compact/microCompact.ts:458` —— 最近证据至少保留一份。**只取这一条原则，不引入四层压缩体系、不引入哨兵替换、不引入可压缩工具白名单。**

### 验收

| # | 用例 | 期望 |
|---|---|---|
| 1 | 复核的复现场景（system + user + 一组工具结果，maxCtx=12000） | 截断后**最新工具结果仍在**，或以带明确截断标记的形式在 |
| 2 | 单组工具结果本身超预算 | 按①②顺序削减，保留工具名与 id，**不得整组消失** |
| 3 | 截断标记内容 | 包含原始字节数与已丢弃字节数，可从输出中直接读出 |
| 4 | 预算极端不足（①②削到下限仍超） | 走既有恢复路径或明确报错；**用例须证明不会发出超预算请求** |
| 5 | 正常多组历史 | 截断行为不变，无孤儿 tool_result（不得破坏已有 C-8 成对丢弃） |
| 6 | **C-10 回归** | 短历史场景仍然会走压缩或截断，**不得因新增保护而退回"既不压缩也不截断"的逃逸口** |
| 7 | 保留下限 | 强制为 1，用例覆盖边界（0 组、1 组、2 组） |

## F2 —— NDJSON 必须表达失败尝试与最终答案的关系

### 问题

位置：`agent/netresilience.go:56`、`324`；`agent/events.go:156-158`、`299-300`。

content delta 立即写入协议；重试时 reset 只清 CLI 缓冲，**未向协议消费者提供撤销、替换或 attempt 边界**。

复核已用 HTTP mock 独立复现：第一次返回 `FAILED_ATTEMPT` 后异常 EOF，第二次正常返回 `FINAL_ANSWER`。内部返回值是 `FINAL_ANSWER`，**协议却依次发出两条 assistant_delta，消费端只能拼出 `FAILED_ATTEMPTFINAL_ANSWER`**。

**每行都是合法 JSON，但"每行可解析"不证明语义正确。** 上一轮的验收标准只验了可解析性，漏了这个。

### 改法

- 定义**最小的**失败尝试废弃 / 最终替换语义。**字段设计由你决定**，但必须满足：消费者能明确知道哪些已发出的 delta 应当丢弃，**不得让前端靠文本内容猜测**。
- **命名约束**（`Direction-Decisions.md` 决策四 4.2：事件命名沿用 Claude Code，不自创）：Claude Code 有对应概念的，沿用其命名；**没有对应概念、必须自创的，在报告中写明自创了什么、为什么找不到对应项**。
- **不要为此引入新的架构层。** 最小可用即可（例如 attempt 序号 + 显式的 reset/discard 事件）。
- 三种路径分别验证：异常 EOF 后重试成功、重试后最终失败、正常一次成功。
- **重试本身必须对用户可见**（§0.5 第 3 条）：CLI 侧至少一行，说明这是第几次尝试、上次为何失败。已有则复用，不得新建机制。

### 验收

| 用例 | 期望 |
|---|---|
| 首次异常 EOF + 重试成功 | 消费者按协议还原出的最终文本 == 内部返回值（不含失败尝试残留） |
| 重试后最终失败 | 消费者能明确判定本轮失败，不把残留 delta 当作答案 |
| 正常一次成功 | 行为不变 |
| 契约同步 | 新增字段/事件已按「全局验收 #10」写入 `api-contract.md` |

## F3 —— 自定义会话文件名不能恢复

### 问题

位置：`agent/main.go:442-452`；`agent/session.go:414`。

`newSession` 按文件名生成身份，随后 `openSessionFor` 用生成的 taskID 覆盖；加载元数据时又要求 taskID 与文件名一致。

已独立复现：创建 `custom.jsonl` 写入一条消息后关闭，再加载元数据立即失败：
`session task identity mismatch: metadata=generated-task filename=custom`

### 为什么必须现在修

显式 `--session` 的记录既不能用于中断恢复，也**不能作为 GUI 的会话关联基础**——前端的会话列表与恢复功能都要建在这上面。

### 改法

- 统一 session / task / filename / manifest 的关联规则。
- **不得通过移除所有身份校验来解决**——checkpoint 与 manifest 仍依赖 task 身份。
- **schema 约束**：`Direction-Decisions.md` 决策四 4.1 已定死会话记录字段（`uuid` / `parentUuid` / `timestamp` / `sessionId` / `cwd` / `version` / `role` / `content` / `tool_calls`）。**本项不得新增顶层字段。** 若确实需要新增才能统一身份，**停止并报告**，不要先写了再说。
- 身份不一致时的报错必须说清**哪个值来自哪里**（metadata / filename / manifest），不得只说 mismatch（§0.5 第 6 条）。

### 验收

| # | 用例 | 期望 |
|---|---|---|
| 1 | 自定义名称 `--session custom` 创建后重新加载 | 成功，不再 mismatch |
| 2 | 默认名称会话 | 行为不变 |
| 3 | 旧格式会话文件 | 能加载，或给出明确的不兼容报错（二选一，报告中说明选了哪个及理由） |
| 4 | 恢复后继续追加消息再次恢复 | 成功 |
| 5 | 工作区不一致（在 B 目录恢复 A 会话） | 明确报错，错误信息含两个工作区路径 |
| 6 | 顶层 schema | 与决策四 4.1 逐字段一致，无新增字段（附 diff） |

**因此本项要做两件事：按现行规格重做实现，并修改固化了旧规格的测试。** 这是本任务包中**唯一**允许修改既有测试断言的地方——它们固化的是已被推翻的裁决，不是产品正确性。

**允许修改的范围（v2 更正：不止一个测试）**

已知四组：`agent/skills_test.go:108`、`agent/permissions_test.go:184`（`/outside` 子用例，`/git` 子用例不动）、`agent/pathpolicy_test.go:48` 与 `:122` 中的外部读/外部写拒绝断言（见下节裁决）。**动手前先 grep 全仓**，把所有固化「工作区外写拒绝 / 工作区外读拒绝」旧规格的测试一次性列全，连同每处现有断言报告后再统一修改——**不要发现一处改一处**。

修改必须满足：

- **是反转 + 补可见性，不是删除。** 外部写的用例改为断言：**写成功执行**，且**事件流、审计、任务结束摘要三处均可见**。只删断言不补可见性验证 = 净损失覆盖，不接受；
- **测试函数名一并改。** 改完断言但名字仍叫 `...StillDeniesOtherOutsideFiles` 之类，等于在源码里留一条谎；
- **同文件中以下断言一律不得改动**：`.git` 内部文件 write/edit 拒绝、路径穿越 / junction / hard link 解析、只读模式、文件新鲜度校验；
- **「用户显式配置 deny 规则后，在放行档位下仍然生效」必须保留或补上。** 取消的是内置的不可覆盖边界，不是权限引擎——用户配了 deny 就得挡住；
- 报告中逐处给出：改前断言、改后断言、它固化的是哪条已被推翻的裁决；
- **「三处可见」若在该测试层级够不到**（任务结束摘要多半够不到），如实写明并在够得到的层级补覆盖，**不得因为不方便就只验事件流与审计、然后声称三处都验了**。

**本节取代 `Direction-Decisions.md` 决策五第二条与 `review.md` F4 的规格描述**（见 §0.1）。

### 现行 N2 规格（**以下为准，不要再参考任何旧版本**）

**只改默认值与可见性，不改权限引擎本身**（权限引擎已建成，不要重构、不要拆）。

- 默认档位 = **放行**；
- **deny 规则默认留空。** 用户已明确要求完全控制操作系统，**不设不可覆盖的路径边界**；
- **唯一保留的 deny：`.git` 目录内部文件的直接 `write` / `edit`。** 理由与权限无关——用文件工具直接改 `.git` 内部结构从来不是正常操作（正常走 git 命令），一旦改坏，checkpoint 与 rollback 整套安全网失效。这是防止 agent 拿错工具，不是限制用户；
- **工作区外的读：放行**（`read` / `tree` / `ls` / `grep` 一律放行，不限于个人 skills 目录）；
- **工作区外的写：放行，但必须三处可见**——事件流、审计、任务结束摘要：

```
本次任务在工作区外写入的文件：
  1. D:\deploy\app.exe
  2. C:\Users\user\.config\tool.ini
以上不在 checkpoint 覆盖范围内，无法通过 rollback 回退。
```

> **裁决理由（不要再讨论）**：任何只加在 `write` / `edit` 上的工作区外写限制都是自相矛盾的——`shell` 一行重定向即可绕过，结果只是把行为从可审计路径推向不可审计路径。历史上 agent 在用户主目录自造文件那次，问题本质是**用户不知道发生了什么**，解法是可见而非禁止。
>
> 需要路径边界的团队可自行配置 deny 规则，用户文档中给出配置示例。

### 必须保留的既有能力（**不得因放宽而丢失**）

路径解析的**正确性**与权限是两回事，解析能力全部保留：

- junction / reparse point 的最终路径解析（`GetFinalPathNameByHandle`）；
- hard link 的**多链接检测**（**v2 更正**：当前实现只能检测链接数 > 1 后整体拒绝，**无法枚举其他名称**——早前把它描述为"最终路径解析"不准确，见下节裁决）；
- `.git` 元数据保护（**不因间接路径而失效**）；
- 只读模式；
- 文件新鲜度校验。

**不得为了"变绿"弱化上述任何一项。**

### 解析结果决定判定，路径怎么拼不决定（**v2 追加裁决**）

解析的作用是**知道这次操作最终落在哪**，不是拒绝。否则同一个外部文件"直接写路径能读、经 junction 读被拒"，权限取决于路径写法——那不是安全边界，是行为不一致，模型撞上去也得不到可理解的解释。

- 解析后落在工作区外的**读**：放行。直接路径 / junction / hard link 一视同仁；
- 解析后落在工作区外的**写**：放行，并**计入「工作区外写入清单」、三处可见**。经 junction 落到外部的写**尤其必须计入**——用户看到的是一个工作区内的路径，会理所当然以为它在 checkpoint 覆盖范围内，**系统不能让它看起来被覆盖**；
- **三处例外，保持拒绝**：
  ① checkpoint 不得跟随 junction 走出工作区（`agent/pathpolicy_test.go:101` 原样保留，理由是 rollback 完整性，与权限无关）；
  ② `.git`；
  ③ **hard link 的 write / edit**（详见下）。

**关于 ③ hard link（v2 追加）**

现有实现只能检测"链接数 > 1"，无法枚举其他名称（`Resolve` / `ValidateOpenFile` / `resolveExistingPrefix`，`pathpolicy_windows.go`）。**F4 敢放行工作区外写，靠的是三处可见；hard link 恰恰给不出这个可见性**——系统不知道本次写入还影响了哪些名称，也无法保证另一个名称不在 `.git` 里。**可见性做不到就不放行**，这与 F4 是同一条原则，不是它的例外。

因此：

- **write / edit 维持拒绝**，但**必须改拒绝理由**。现有错误文本把"我不知道"包装成了"这是规则"，属 §0.5 第 6 条禁止的行为。改为说清事实：该文件存在多个硬链接名称，无法确定本次写入实际影响哪些路径，因此拒绝；
- **read 放行**。读不存在"还影响了哪些路径"的问题，没有可见性缺口，拒绝无依据。`pathpolicy_test.go:122` **只反转读那一条**，write / edit 两条保留但同步更新断言措辞与错误文本；
- **本任务包不实现 `FindFirstFileNameW` / `FindNextFileNameW` 名称枚举。** 记入 `f1f4-findings.md`，写明三点：Vista 起可用，Win7 无兼容问题；该 API 返回的是卷内相对路径，需配 `GetVolumePathName` 拼回完整路径；待真实使用中出现 hard link 场景再评估；
- 该拒绝形态需写入 `api-contract.md`：前端要能区分"权限不足"与"系统无法确定影响面"——两者给用户的下一步动作不同。

由此产生的后果，**照此处理**：

- `pathpolicy_test.go:48` / `:122` 中**属于"外部读被拒""外部写被拒"的断言**同样固化了已被推翻的规格，按 F4 同一规则反转（反转 + 补可见性，不是删除），逐条记入报告；同文件中 `.git` 相关的、以及验证解析本身是否正确（能否判定最终落点）的断言**全部保留**；
- **严禁为保住旧断言而新增拒绝逻辑。** 若保持某条旧断言为绿需要写出本文件未要求的特判分支（例如"解析时穿过 reparse point 即拒绝"），那是超范围（§1.1）——反转断言，不要写特判。**为变绿而新增代码，与为变绿而弱化断言，是同一种错误的两个方向。**
- 若按本裁决实现需要对 `pathpolicy_windows.go` 做**结构性改动**（不只是删掉边界判断那一步），**停止并报告**——那说明解析与权限在代码里没有分开，属另一件事。

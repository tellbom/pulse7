## G1 —— 后台任务 ID 会碰撞（**最高优先级，阻断阶段三 B4**）

### 问题

位置：`agent/tasks.go:114`（`time.Now().UnixNano()` 生成 ID）、`:147`（`m.tasks[id] = task`）。

Win7 amd64 20 次诊断：`TestExitSummaryListsHarvestedAndDetachedTasks` 失败 15 次，**15 次失败的两条 `[task] STARTED` 全部同 ID**；5 次通过的全部不同 ID。Windows 时钟粒度粗，连续两次 launch 可拿到同一时间戳，第二次登记**直接覆盖**第一次。map 写入有锁，锁挡不住键相同。

### 为什么必须现在修

**这是产品缺陷，不是测试缺陷。** 阶段三 B4 的后台任务表、`task_output`、`task_kill` 全部以 task_id 为索引，输出文件名也是 `data\tasks\<task_id>.output`。快速连开两个后台任务 → 第一个的记录、输出文件、PID 被无声覆盖。**B4 建在这个 ID 上，必须先修。**

### 改法

- 保证**同一进程内 task ID 绝不重复**。
- 具体方案由你选定并说明理由，但必须满足：ID 仍可读、仍可安全用作文件名；**不新增配置项、不新增依赖、不引入全局状态**；生成与登记之间的窗口必须被消除（不是"降低概率"）。
- **不得修改该测试的断言使其变绿。**

### 验收

| # | 用例 | 期望 |
|---|---|---|
| 1 | 连续快速启动 ≥50 个任务 | ID 全不重复（附实测输出） |
| 2 | `TestExitSummaryListsHarvestedAndDetachedTasks` 连跑 20 次（Win7 amd64） | 全部通过；如仍有失败，如实记录不掩盖 |
| 3 | 两条 STARTED 记录 | ID 不同 |
| 4 | 现有 tasks 相关用例 | 无退化 |

## G4 —— `dirty-files` 计数的比较基准与它的名字不一致

### 问题

位置：`agent/gittools.go:123-126`、`:171-181`、`:214-223`、`:130-145`。

已查明：全局 `core.autocrlf=true`，普通索引存 LF、工作区为 CRLF；`CheckpointAs` 为保全字节强制 `autocrlf=false`，临时索引存下 CRLF，于是 2524 个文本 blob 相对 HEAD 全成 staged M。逐 blob 验证 2524/2524 仅 LF→CRLF 差异，实际任务只改 1 个文件。

**存储本身没错**（私有 ref、不动业务 HEAD、字节保全是有意为之）。错的是**这个数对用户表达的含义**。

另有一处同类毛病：`CheckpointAs` 用 `CombinedOutput` 按换行计数**且忽略 status 的 error**——本次 2524 不是警告行堆出来的，但该实现**永远无法保证自己数的是文件**。

### 裁决（**v2 更正：原定义与实现规定冲突，以本节为准**）

原文件的语义定义「本次任务在工作区内改动的文件数」**是错的**，与它自己规定的实现（普通索引 status）在两处对不上：① 首次自动 checkpoint 拍在任何修改之前，此刻 status = 0；② 任务开始前已有未提交改动时，status 会把旧改动一并计入。**这是任务书的规格缺陷，不是实现问题。**

**采纳「采集时刻普通索引 status 的变更文件数」为计数基准。**

理由：这个数出现在 checkpoint 上，而 checkpoint 是回滚安全网。用户在那一刻要知道的是**我刚拍下的快照里有多少东西不同于 HEAD**——那正是工作区相对 HEAD。任务开始前就存在的改动**确实被这次 checkpoint 收了进去、也确实能被 rollback 还原**，把它们计入是正确的，不是污染。

**但既然基准是工作区相对 HEAD，标签必须照实说。** 引发本项的根问题从来不是数错了——2524 这个数是准确的——而是**名字与基准不一致**，让人读成"本次改了 2524 个文件"（§0.5 第 6 条）。

因此：

- 计数基准 = **采集时刻普通索引的 status**（与用户自己敲 `git status` 同一基准）；
- **同时修改该字段的展示文案**，明确表达为「工作区相对 HEAD 的变更文件数」，不再暗示"本次任务"。字段名若一并改动，报告中写明改前/改后；
- **首次 AUTO checkpoint 在修改之前报 0，属正常，不是缺陷**；
- checkpoint 的**存储行为不变**：临时索引仍强制 `autocrlf=false` 保全字节。**不统一换行、不改 `core.autocrlf`**；
- **不得再从 `CombinedOutput` 按换行数数**：改用 `--porcelain` 的机器可解析格式逐条解析；**status 返回 error 时必须明确报错，不得忽略**。

**「本次任务改动了哪些文件」是另一个需求**，属任务结束摘要范畴（与 F4 的工作区外写入清单同层）。**本节点不实现**，记入 findings 并列为阶段三契约条目。

### 验收

| # | 用例 | 期望 |
|---|---|---|
| 1 | R1 场景**首次 AUTO checkpoint**（干净克隆，模型尚未改动） | **0**（这是正确结果，不是缺陷） |
| 2 | R1 场景**模型改动之后**的 checkpoint（与基线成对） | **1**，即实际改动的那个文件 |
| 3 | 任务开始前工作区已有 N 个未提交改动 | 计数**包含**它们（用例固化该语义） |
| 4 | 展示文案 | 明确为「工作区相对 HEAD」，不再暗示"本次任务" |
| 5 | checkpoint 存储字节 | 与改动前一致（附 checkpoint tree 或 blob 比对） |
| 6 | status 执行失败 | 明确报错，不静默产出一个数 |
| 7 | 计数来源 | 不再依赖 `CombinedOutput` 行数（附 diff） |
| 8 | 既有 checkpoint / rollback 用例 | 无退化 |

## G5 —— deny 规则按解析后的目标匹配（**记录现状，不改行为**）

### 为什么要处理

F4 取消内置边界的理由是"需要路径边界的团队自行配置 deny 规则"。**如果别名写法会悄悄失效，那个出口就没有兑现。**

### 改法

1. **用户文档**中写明：allow / deny 规则按**解析后的最终目标**匹配，请按最终路径书写规则；给一个 junction 的具体例子说明按别名写不会命中。
2. **增加测试固化当前行为**：按最终目标书写的规则 → 生效；按别名书写的规则 → 不命中。

**这是把现状写清楚，不是改行为。** 若你认为应当改成两者都匹配，**停止并报告**，不要自行实现。

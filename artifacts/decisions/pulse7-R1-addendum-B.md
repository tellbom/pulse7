VM 恢复（**用户已授权控制宿主机**）  ### 1.1 现状判定  TCP 2222 可建立连接但 8 秒内无 SSH banner，另一次发送 identification 被远端 RST。这不是网络不通，是 **sshd 或整个用户态失去响应**。  本项目有明确前例：Win7 在大量进程之后用户态失去响应，Win7 比 Win10/11 脆弱得多。上一轮在该 VM 上跑了全量测试与进程生命周期用例，符合这一模式。  ### 1.2 授权与升级顺序（**按序执行，每一步失败才进下一步**）  | 步 | 动作 | 前置 | |---|---|---| | 1 | 客户机内软重启（VMware Tools guest restart / `shutdown /r`） | 首选，直接执行 | | 2 | 客户机电源软关机后再开机（guest shutdown → power on） | 第 1 步失败或 5 分钟内未恢复 | | 3 | 宿主机强制 reset（**hard reset**） | 第 2 步失败；**执行前在报告中写明第 1、2 步各自的失败表现** |  - **每步之间等待并重试 SSH，最多 5 分钟**； - **总尝试上限 2 轮。** 两轮后仍不可达则**停止并等待人工**，不要继续尝试其他手段； - 每一步的时间戳、命令、返回、SSH 探测结果全部记入 `artifacts/f1f4-evidence/vm-recovery.json`。  > 任务书 §1.4 原写"不对 VM 做硬复位"。**本文件在上述顺序与上限内解除该限制**，其余环境纪律不变。  ### 1.3 恢复后的强制核对（**先做，再谈跑测试**）  1. 记录 VM 的**本次启动时间**（`systeminfo` 的 System Boot Time 或等价命令），写入 `vm-recovery.json`； 2. 确认 `C:/Users/user/f1f4-validation` 及其下 live 夹具仍在，列目录存档； 3. **本轮之后产生的每一份 Win7 日志，其时间戳必须落在本次启动窗口之内。** 沿用既有 Gate 纪律：**跑前删旧日志**，防止读到上一次残留当成本次结果。  > 依据项目既往教训：曾读到挂死实例留下的旧日志当作新结果。**假 PASS 是最贵的错误。**  ### 1.4 凭据  本次动用宿主机凭据即视为**凭据扩散再增一次**。**不要在任何报告、日志、JSON 中写出宿主机或 VM 的密码、密钥内容**，只记"已使用宿主机管理员凭据"。凭据轮换仍是人工事项，不在本任务包范围内。  ---  ## 2.

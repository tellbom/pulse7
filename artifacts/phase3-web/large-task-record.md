# ChatGPT 对"pulse7 是否放开轮数限制"的研判（2026-09-14 09:57 送达并收到回复）
## 结论：支持交互模式默认不限轮，但须成体系实现
- 场景×默认值建议：GUI/REPL 交互任务默认**不限轮**（界面明确展示"不限轮"，不显示虚假大数字）；非交互 CLI/脚本默认 100 轮（严格执行不自动抬高）；有限轮数定位为"用户显式选择的执行预算"。
- 实现要点：定义 max_rounds=0 为不限轮，须区分"未配置"与"显式 0"；当前实现不支持该语义，不能只改默认数字——配置加载、API 校验、循环、状态展示、测试需一起调整；已有配置的 100 保留由用户切换。
- 四维判断：①防失控——轮数是粗预算，区分不了认真探索与死循环（一轮可多工具、压缩产生额外请求，轮数≠费用）；保留可选硬上限+展示累计轮数/工具数/耗时/token 用量，不自动抬预算。②可中断——交互不限轮的前提是停止入口始终可用（覆盖输出/压缩/工具等待三态）；用户离开后不会主动止损。③上下文防线——多次压缩后继续运行证明机制能支撑长任务，但压缩限制的是请求上下文非累计开销，也不保证关键事实不丢失；不要因不限轮取消这些边界。④产品定位——开发助手要经历探索/实现/调试/验证，100 轮难概括合理工作量；**现代硬件上的 Win7 不构成短预算依据**（直接回应本方背景）。
- 对"禁止再读"强约束的告诫：不要固化"读 N 轮必须写码"或自动注入禁读指令——可能迫使模型在未核实契约时猜着实现；重复探索应先做**事实可见性**（提示近期重复读取了哪些路径，由用户决定干预），不做自动行为裁决。
- 对本方轮数判据的印证：继续下一轮的依据=工具调用执行回填后需模型跟进；pulse7 当前按 ToolCalls 是否为空判断、不依赖 stop_reason——与 Claude Code 同构，无需重写。
- 诚实边界：本案例支持取消固定交互上限，但不支持宣称"模型死循环已解决"；go build/vet 通过不能替代 RBAC 语义与权限回归。

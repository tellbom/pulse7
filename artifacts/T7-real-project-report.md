### R2（探索）：说明项目入口和主要模块分工，不修改任何文件

| 指标 | 值 |
|---|---|
| 轮次 | **30（撞上限）** |
| 工具调用 | ls×**105**, read×26, glob×10, shell×2 |
| 总耗时 | ~340 秒 |
| 上下文压缩 | **22 次**（audit 实证） |
| 撞 30 轮上限 | **是** |
| 最终收敛 | **否**（空终答，因撞上限） |
| **工作区改动** | **零** ✅（`.claude/` 目录是 agent 数据目录，非项目改动） |
| 模型找错文件 | 否（未读错文件） |
| 读大量无关 | **是**（26 次 read 读了大量配置/代码文件） |
| 在检索上反复打转 | **是**（105 次 ls 是病态行为：模型试图遍历每个子目录） |

**失败形态分析**：

1. **ls×105 是核心问题**：模型不知道"看顶层 + 几个关键文件就够了"，试图穷举每个子目录
2. **22 次压缩 = 上下文管理失败**：每次 ls + read 添加大量内容 → 触发压缩 → 压缩丢弃了模型刚看到的信息 → 模型重新 ls/read → 死循环
3. 模型没有能力在大量碎片化探索后"停下来综合"——它一直在收集信息但从未切换到总结模式

**这本身就是最有价值的失败样本**：问题不在检索速度（rg 也救不了 105 次 ls），而在探索策略。

## 结论：手写 grep 在这个规模上够用还是不够用？

**够用。**

判据：这个项目（5829 文件 / 136MB / 230 个 .cs）上，自写 grep 的预估耗时约 300-500ms（Win7），远低于一轮 LLM 调用耗时（3-10 秒）。模型每次任务只用 grep 2-10 次，检索不是瓶颈。

**真正的瓶颈是探索策略**：R2 的 105 次 ls 和 22 次压缩证明，模型不知道何时停止探索。这需要提示词优化（"先看顶层，选择性深入"），不是工具优化。

如果项目增长到 50,000+ 文件（500MB+），自写 grep 可能需要 3-5 秒/次，那时才需要集成 ripgrep。当前规模下 rg 的收益是"快 6 倍但只省 200ms"，对整体任务耗时影响 <2%。

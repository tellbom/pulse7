# T5: S2 数据异常结论

## 判定：提示词调优的副作用（非统计口径变化）

| | RC 0.1（调优前） | PreRC02（调优后） |
|---|---|---|
| 轮次 | 7 | 13 |
| write+edit | 2 | 8 |
| 最终结果 | ✅ 正确 | ✅ 正确（最终文件一致） |
| 行为 | 干净：read → edit ×2 → verify | **循环**：edit ×2 → type检查 → re-edit ×2 → xxd查编码 → python repr → re-edit ×2 → **全文件重写** ×2 → verify |

## 根因

调优后的系统提示词加入了 **"动手前先 checkpoint，改动后验证"**。模型对此过度执行：每次 edit 后都用 `type` 检查文件内容，发现 cmd shell 的 GBK 编码与 Go 写入的 UTF-8 有差异（`type` 输出乱码），以为改错了，于是 re-edit → 再检查 → 再乱码 → 再 re-edit……最终放弃 edit 改为 write 全文件重写（用完整 content 覆盖，绕过精确匹配）。

## 8 次"写"的具体分解

| # | 工具 | 目标 | 原因 |
|---|---|---|---|
| 1 | edit | utils.py | 正常首次修改（加 trim） |
| 2 | edit | main.py | 正常首次修改（接入 trim） |
| 3 | edit | utils.py | re-edit：type 检查后认为内容异常 |
| 4 | edit | main.py | re-edit：同上 |
| 5 | edit | utils.py | re-edit：xxd/repr 检查后再次修改 |
| 6 | edit | main.py | re-edit：同上 |
| 7 | **write** | utils.py | **全文件重写**：放弃 edit，直接覆盖 |
| 8 | **write** | main.py | **全文件重写**：同上 |

## 影响

- 任务仍然收敛且结果正确（文件最终一致）
- 多花了 6 轮和 ~30 秒
- **核心问题**：shell `type` 在 GBK 控制台读 UTF-8 文件必然乱码，模型不知道这是正常现象

## 建议（本轮不改，留到下一轮）

1. 在系统提示词或 edit 工具描述中加一句："`type` 命令显示中文可能乱码，这是正常的编码差异，不代表文件损坏"
2. 或在 shell 工具返回中检测到 `type` + 乱码时附加说明
3. 或考虑将"改动后验证"从系统提示词中移除或弱化（"如需验证可运行"而非"改动后验证"）
